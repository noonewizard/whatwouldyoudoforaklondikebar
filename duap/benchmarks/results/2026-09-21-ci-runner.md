## Interpretation

These are measurements of this code on this machine on this date. They are
not projections, and nothing below multiplies a per-core figure by a core
count.

### What dominates ingest

Single-threaded ingest is **7,829 events/s**, at 127.7 us per event. The
pipeline decomposes roughly as:

| Component | measured | share of 127.7 us |
|---|---:|---:|
| Ed25519 envelope verification | 49.8 us | 39% |
| Authorization evaluation | 15.6 us | 12% |
| Canonical encode (digest computation) | 11.1 us | 9% |
| Canonical decode (payload open) | 7.1 us | 6% |
| Remainder: dedup, fingerprinting, aggregation, storage, provenance | ~44 us | 34% |

Signature verification is the largest single cost, which is what one would
expect and is the reason batch verification is the first optimisation worth
attempting. It has not been attempted.

### Three findings this run produced

1. **`log.inclusion_proof` is O(n), not O(log n).** Generating one audit
   path in a 100,000-entry tree takes 14.99 ms, while *verifying* the same
   path takes 2.5 us. The reference `MerkleLog` recomputes sibling subtree
   roots on demand rather than caching them. This is acceptable in a
   reference implementation and unacceptable in a gateway endpoint; recorded
   as `security/findings.md` PERF-01 with the production design (cached
   level hashes or a tile-based layout).

2. **Canonicalisation costs 11.1 us per event**, because the serde bridge
   encodes with a general CBOR codec and then normalises. That was a
   deliberate choice (one definition of canonical form, shared with the
   network path) and it is measurably not free: about 9% of ingest. A
   direct canonical serialiser would remove most of it at the cost of a
   second definition of the encoding. Not changed; recorded so the trade-off
   is visible rather than assumed.

3. **The post-quantum cost is concentrated in signing, not verifying.**
   ML-DSA-44 signing is 690.7 us against Ed25519's 47.4 us -- 15x -- while
   verification is only 2.2x slower. For DUAP this is the favourable
   direction: events are signed once by an agent and verified once by a
   clearing node, but receipts are signed once and verified many times by
   subjects and auditors. The hybrid suite costs 3,096 bytes per event
   envelope against 665 for Ed25519, a 4.7x size penalty that dominates the
   storage decision rather than the CPU one.

### Size at scale, stated as arithmetic rather than as a claim

One event envelope is 665 bytes signed with Ed25519. Storing 10^9 events
therefore costs 665 GB before indices, compression or replication; at 10^12
events it is 665 TB. Those are multiplications of a measured size, not
measurements, and they exclude the index overhead that a real store adds.
The transparency log is cheaper by three orders of magnitude because it
commits to batch roots: 129 bytes per entry, one entry per batch.

### What this run does not measure

- Concurrency. Every scenario is single-threaded. No claim is made about
  scaling across cores or hosts.
- Durable storage. The ingest scenario uses the in-memory store; SQLite was
  not exercised here.
- Network. No HTTP, no TLS, no serialisation across a socket.
- Cold caches, contention, or long-run memory behaviour.
- Cost per million or per billion events in currency terms, which depends
  on an instance price this harness has no business guessing.
