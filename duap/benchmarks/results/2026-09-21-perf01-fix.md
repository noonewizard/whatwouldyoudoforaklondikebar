## What changed, and what it cost

| Scenario | Before | After | Change |
|---|---:|---:|---|
| `log.inclusion_proof` | 14.99 ms | **3.3 us** | ~4,500x faster |
| `log.append` | 108 ns | **1.1 us** | ~10x slower |

### PERF-01 is closed

Generating one audit path in a 100,000-entry tree went from 14.99 ms to
3.3 us, and the true factor is larger than the ratio suggests because this
machine was slower on every untouched scenario.

The old path recomputed sibling subtree roots from leaves at every level,
so proof generation walked the whole tree: O(n). `MerkleLog` now caches the
roots of complete subtrees level by level, and the RFC 6962 split rule
makes every left child of the proof recursion an aligned complete subtree —
so each level is a cache lookup and the recursion only descends the right
spine.

The security consequence is the point of the exercise. At 14.99 ms per
request, the gateway's `/v1/log/proof` endpoint let an attacker spend
15 ms of server time on a cheap request; at 3.3 us it does not. The
endpoint should still be rate-limited, but it is no longer a
denial-of-service lever by construction.

### The cost, stated plainly

**Appends got about ten times more expensive**, from 108 ns to 1.1 us, and
roughly 6-7x of that is real once the slower machine is discounted. That is
the amortised cost of hashing interior nodes as they complete — work the
old implementation deferred and then repeated on every proof.

It is the right trade for this system and it is worth being explicit about
why, rather than presenting a 4,500x improvement with no mention of what
paid for it:

- The tree has to be hashed eventually. Hashing each interior node once on
  append beats recomputing it on every proof request.
- Appends are internal and batched; proofs are served to counterparties on
  demand, so the expensive operation is now the one an attacker cannot
  trigger.
- Even at 1.1 us, append is not close to being the bottleneck: ingest is
  207.4 us per event on this run, of which append is about 0.5%.

Memory roughly doubles: n leaf digests plus at most n-1 interior ones. For
the 100,000-entry tree that is about 6.4 MB against 3.2 MB.

### What this does not establish

The cache is an optimisation and must never become a second definition of
the tree. `root_of` remains the reference construction transcribed from
RFC 6962 section 2.1, and
`crates/duap-provenance/tests/merkle_cache.rs` asserts the two agree on
every root, every audit path and every consistency path for every tree size
in 0..=130 — the range that covers every shape the split rule produces.
Five tests, including that a proof still verifies with the log dropped and
that appending after a proof was taken does not invalidate it.

No concurrency, durability or network behaviour is measured here, as
before.
